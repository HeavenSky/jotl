# Convert between JSON Schema and TypeScript

**English** · [简体中文](../zh/docs/ts-conversion.md)

This page shows how to turn a JSON Schema 2020-12 document into TS declarations with `schemaToTs`, and read a declaration file back with `tsToSchema`. It assumes you have installed `@jotl/convert` as in the [README](../README.md#get-started).

`schemaToTs` writes the keywords that types cannot express as JSDoc tags, and `tsToSchema` reads the same notation back. Both directions share one [tag protocol](./tag-protocol.md). **Reading a generated `.d.ts` back with `tsToSchema` gives a schema deeply equal to the original**; the shared samples `fixtures/*/types.d.ts` are the test baseline.

## Convert a schema and read it back

```ts
import { schemaToTs } from "@jotl/convert";
import { tsToSchema } from "@jotl/convert/from-ts";

const schema = {
	$schema: "https://json-schema.org/draft/2020-12/schema",
	$ref: "#/$defs/Page",
	"x-ui": { version: 1 },
	$defs: {
		Page: {
			type: "object",
			properties: {
				title: {
					title: "标题",
					type: "string",
					maxLength: 20,
					default: "欢迎",
					errorMessage: { maxLength: "最多 20 字" },
				},
				count: { type: "integer", minimum: 1 },
				mode: {
					type: "string",
					oneOf: [
						{ const: "light", title: "浅色" },
						{ const: "dark", title: "深色" },
					],
				},
				cover: { type: "string", format: "uri", "x-ui": { widget: "image" } },
			},
			required: ["title"],
		},
	},
};

const ts = schemaToTs(schema); // diagnostics: []
const back = tsToSchema(ts.value!, { fileName: "page.d.ts" }); // back.value is deeply equal to schema
```

`ts.value` (with the default `en` language):

```ts
// Generated by Jotl. Do not edit.

export interface Page {
	/**
	 * @title 标题
	 * @maxLength 20
	 * @defaultValue "欢迎"
	 * @errorMessage `{"maxLength":"最多 20 字"}`
	 */
	title: string;
	/**
	 * @asType integer
	 * @minimum 1
	 */
	count?: number;
	/**
	 * @enumTitles `{"light":"浅色","dark":"深色"}`
	 */
	mode?: "light" | "dark";
	/**
	 * @format uri
	 * @widget image
	 */
	cover?: string;
}

export default Page;
```

The schema carries `"x-ui": { version: 1 }` on the root because `@jotl/core`'s compiler writes it, and `tsToSchema` writes it back whenever there is a root type. Without it the round trip differs by exactly that key.

## Choose the entry point

`schemaToTs` comes from the main entry `@jotl/convert`, and `tsToSchema` only from the subpath `@jotl/convert/from-ts`. The package depends on a pinned `typescript@6.0.3`, and only `tsToSchema` uses it.

The main entry, including `schemaToTs` and all migration APIs, does not reference `typescript`, so browser bundles and extensions that use only the main entry do not bundle the compiler. Importing from `@jotl/convert/from-ts` bundles the entire compiler; the build guard in [`apps/playground/vite.config.ts`](../../../apps/playground/vite.config.ts) fails the build when `typescript` ends up in the output. Running `tsToSchema` in a browser has not been verified; see [Known limitations](#known-limitations).

## What schemaToTs outputs

The output layout (generated header, declaration order, indentation, default export) is described in "TS output format" in the [shared fixtures README](../../../fixtures/README.md). When the root schema is not a `$ref` to `$defs`, it is output as a `Root` type and default-exported, with a `JOTL2006` warning.

Keywords without a TS notation are dropped with `JOTL2002`; the [tag protocol](./tag-protocol.md) lists which ones.

## What tsToSchema accepts

`tsToSchema` converts by syntax tree only, without type checking. The root is the declaration whose comment has `@root`, or the default export when there is none.

- Supported: `interface`, `type`, `export default` (including `export { X as default }`), `Array<T>`, `Record<string, T>`, tuples and `readonly`. The names of named tuple members become the `title` of their positions.
- Unions: discriminated unions become `oneOf`, literal unions containing `null` become `anyOf: [enum, { type: "null" }]`, `(A | B) | null` becomes `anyOf: [the union of A and B, { type: "null" }]`, and other unions become `anyOf`.
- Intersections only accept references, combined with at most one other type and typia tags (see the [tag protocol](./tag-protocol.md) and [Write typia type tags](#write-typia-type-tags)). Several object literals (e.g. `{ a: 1 } & { b: 2 }`) containing only property signatures with pairwise distinct names merge into one open object (merging `properties` and `required`). Other intersections (clashing property names, index signatures, methods and so on) report `JOTL2106`.
- Unsupported constructs report error-level diagnostics: generics, conditional types, mapped types, functions and methods, interface inheritance, other declarations such as `enum`, and computed property names.
- Import declarations only report a `JOTL2108` warning; types from other files are not converted.

## Write typia type tags

With `typiaTags: true`, constraints typia can express are written as type intersections. The output starts with `import { tags } from "typia";`; the import uses an alias when a type is already named `tags`, and is left out when no tag is used.

- `type: "integer"` → `tags.Type<"int32">` (when both bounds are within int32) or `tags.Type<"int64">`, no longer writing `@asType`.
- Numeric and length constraints → same-named tags such as `tags.Minimum<1>`; `pattern` → `tags.Pattern`; `uniqueItems` → `tags.UniqueItems`; `contentMediaType` → `tags.ContentMediaType`.
- `format` is rewritten only for formats typia supports (the list is `TYPIA_FORMATS` in [`src/ts/typia.ts`](../src/ts/typia.ts)); others (such as `color`) are still written as `@format`.
- `default` that is a string, number, boolean or an array of them → `tags.Default`, otherwise still `@defaultValue`.
- `x-ui` that is an object → `tags.JsonSchemaPlugin<{ "x-ui": ... }>`.
- Nullable types tag only the non-`null` part. Interface declarations themselves cannot carry tags, so their constraints are still written as JSDoc. Element-level constraints can be expressed in this mode.

The output type-checks with zero errors against the type definitions of `typia@15.1.0`; other typia versions may have different `tags.Format` values.

`tsToSchema` reads tags imported via `import { tags } from "typia"` (including aliases) and restores them to the keywords above; `tags.Type<"int32" | "int64" | "uint32" | "uint64">` changes `number` to `integer`. Nullable `(T & tags.X) | null` reads back as `type: [T, "null"]`, so typia-mode output round-trips. The import declaration still reports a `JOTL2108` warning; other typia tags, and `tags.X` without the import, report `JOTL2106`.

## Read diagnostics

`JOTL20xx` codes come from schema → TS and `JOTL21xx` from TS → schema; the code table is `TS_DIAGNOSTICS` in [`src/ts/diagnostics.ts`](../src/ts/diagnostics.ts). Diagnostics on TS source carry a line and column with `location.kind = "source"`; diagnostics on the schema carry a JSON Pointer to the node.

## Known limitations

- **Titles of tuple positions survive only as member names.** TS tuple elements have no place for a comment, so `schemaToTs` writes the `title` of each `prefixItems` position as a named tuple member (`[开始: string, 结束: string]`). TS requires a tuple to name all of its members or none, so this works only when every position has a `title` that is an identifier and not a reserved word; otherwise the titles are dropped with `JOTL2002` (see the [tag protocol](./tag-protocol.md)). Put the meaning in the `description` of the array itself if readers of the `.d.ts` need it.
- **`tsToSchema` is untested in browsers.** It runs the classic API of `typescript@6.0.3` with a custom compiler host, which is covered only under Node.js. Run it in Node.js, or test it in your target browser before relying on it.
