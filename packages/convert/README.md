# @jotl/convert

**English** · [简体中文](./README.zh-CN.md)

Read this page when converting between JSON Schema and TS declarations (types + JSDoc tags), hand-writing or proofreading tags in Jotl-generated `.d.ts`, configuring Jotl tags for TSDoc / ESLint, upgrading legacy JSON Schema to 2020-12 in code, migrating Fengdie schemas to Jotl, or interpreting `JOTL20xx` / `JOTL21xx` (TS conversion), `JOTL3xxx` (upgrade) and `JOTL8xxx` (Fengdie) diagnostics; it corresponds to `packages/convert`.
This package has two parts: TS conversion (`src/ts/`), and legacy JSON Schema / OpenAPI upgrade plus Fengdie migration (`src/migrate/`).
The command-line entry for migration is `jotl migrate-schema` (input type detected automatically), see `packages/cli/README.md`.

Diagnostic messages and generated text (generated header, default deprecation text, Fengdie group titles, input detection reasons) follow `@jotl/core`'s global language: the default is English (`en`); call `setLocale("zh-CN")` from `@jotl/core` for Chinese.

## Installation

```sh
pnpm add @jotl/convert
```

Depends on a pinned `typescript@6.0.3`, used only by `tsToSchema` (subpath `@jotl/convert/from-ts`).

## TS conversion

`schemaToTs` outputs JSON Schema 2020-12 as TS declarations, writing keywords that types cannot express as JSDoc tags; `tsToSchema` reads the same notation back. Both directions share one tag protocol, and a generated `.d.ts` round-tripped through `tsToSchema` is deeply equal to the original schema (the shared samples `fixtures/*/types.d.ts` are the baseline).

### Minimal example

```ts
import { schemaToTs } from "@jotl/convert";
import { tsToSchema } from "@jotl/convert/from-ts";

const schema = {
  $schema: "https://json-schema.org/draft/2020-12/schema",
  $ref: "#/$defs/Page",
  $defs: {
    Page: {
      type: "object",
      properties: {
        title: { title: "标题", type: "string", maxLength: 20, default: "欢迎", errorMessage: { maxLength: "最多 20 字" } },
        count: { type: "integer", minimum: 1 },
        mode: { type: "string", oneOf: [{ const: "light", title: "浅色" }, { const: "dark", title: "深色" }] },
        cover: { type: "string", format: "uri", "x-ui": { widget: "image" } },
      },
      required: ["title"],
    },
  },
};

const ts = schemaToTs(schema); // diagnostics: []
const back = tsToSchema(ts.value!, { fileName: "page.d.ts" }); // back.value is deeply equal to schema
```

`ts.value`:

```ts
// 由 Jotl 生成, 不要手改.

export interface Page {
  /**
   * @title 标题
   * @maxLength 20
   * @defaultValue "欢迎"
   * @errorMessage `{"maxLength":"最多 20 字"}`
   */
  title: string;
  /**
   * @asType integer
   * @minimum 1
   */
  count?: number;
  /**
   * @enumTitles `{"light":"浅色","dark":"深色"}`
   */
  mode?: "light" | "dark";
  /**
   * @format uri
   * @widget image
   */
  cover?: string;
}

export default Page;
```

### Public API of TS conversion

| Export | Signature | Notes |
|---|---|---|
| `schemaToTs` | `(schema, options?: SchemaToTsOptions) => Result<string>` | Reports `JOTL2001` when the input is not a schema object; inexpressible keywords are dropped with a `JOTL2002` warning, without affecting output |
| `SchemaToTsOptions.typiaTags` | `boolean`, default `false` | See the typia section below |
| `SchemaToTsOptions.defaultExport` | `string`, a key of `$defs` | The type to default-export; take `defaultExport` from `@jotl/core`'s `compile` result (Jotl's `<default/>`). When absent or not in `$defs`, the root is default-exported; when it differs from the root, the root type's comment gets `@root` |
| `tsToSchema` (exported only from `@jotl/convert/from-ts`) | `(source, options?: TsToSchemaOptions) => TsToSchemaResult` | Input is the text of a single declaration file; with error-level diagnostics `value` is `undefined`. `TsToSchemaResult` extends `Result<JsonSchemaObject>` with `defaultExport?` (the default export's type name, not in the schema; pass it to `@jotl/core`'s `print(schema, { defaultExport })` when printing Jotl to write `<default/>`) |
| `TsToSchemaOptions.fileName` | `string` | Used only as the file name in diagnostic locations |
| `GENERATED_HEADER` `GENERATED_HEADER_EN` | `string` | The first line of generated files (`// 由 Jotl 生成, 不要手改.` / `// Generated by Jotl. Do not edit.`), chosen by the global language |
| `CUSTOM_TAGS` | `readonly CustomTagDefinition[]` | Custom tag names and syntax (`block` / `modifier`) defined by the protocol |
| `TS_DIAGNOSTICS` `tsDiagnostic` `TsDiagnosticCode` | | Code table and diagnostic factory |
| `definedTags` of `@jotl/convert/eslint` | `readonly string[]` | See the lint section below |
| `@jotl/convert/tsdoc.json` | TSDoc configuration file | See the lint section below |

For output layout (generated header, declaration order, indentation, default export) see "TS output format" in `fixtures/README.md`. When the root schema is not a `$ref` to `$defs`, it is output as a `Root` type and default-exported, with a `JOTL2006` warning.

`tsToSchema` converts by syntax tree only, without type checking; the root is the declaration whose comment has `@root`, or the default export when there is none; it supports `interface`, `type`, `export default` (including `export { X as default }`), `Array<T>`, `Record<string, T>`, tuples and `readonly`. Discriminated unions are output as `oneOf`, literal unions containing `null` as `anyOf: [enum, { type: "null" }]`, and other unions as `anyOf`. Intersection types only accept references, combined with at most one other type and typia tags (see the tag protocol and typia sections); multiple object literals (e.g. `{ a: 1 } & { b: 2 }`) containing only property signatures with pairwise distinct names are merged into one open object (merging `properties` and `required`); other intersections (clashing property names, index signatures, methods and so on) report `JOTL2106`. Unsupported constructs (generics, conditional types, mapped types, functions and methods, interface inheritance, other declarations such as `enum`, computed property names) report error-level diagnostics; import declarations only report a `JOTL2108` warning, and types from other files are not converted.

### Tag protocol

Correspondence between keywords and TS notation:

| JSON Schema | TS notation |
|---|---|
| `description` | JSDoc body |
| `title` | `@title text` |
| `$comment` | `@privateRemarks text` |
| `type: "integer"` | Type written as `number`, plus `@asType integer` (omitted when the node is an enum or const) |
| `minLength` `maxLength` `minimum` `maximum` `exclusiveMinimum` `exclusiveMaximum` `multipleOf` `minItems` `maxItems` `minProperties` `maxProperties` | Same-named tag, value is a number |
| `format` `contentMediaType` `contentEncoding` | Same-named tag, value is text |
| `pattern` | `@pattern`, value is a regex |
| `uniqueItems: true` `writeOnly: true` | `@uniqueItems` `@writeOnly` (modifier tags, no value) |
| `readOnly: true` | `@readonly` |
| `deprecated: true` (+ `x-deprecatedReason`) | `@deprecated reason`; without a reason the default text is written, `已弃用.` under `zh-CN` and `Deprecated.` under `en`; either text produces no `x-deprecatedReason` when read back |
| `default` | `@defaultValue JSON` |
| `examples` | One `@example JSON` per example |
| Labeled enum `oneOf: [{ const, title }]` | Type is a literal union, plus an `@enumTitles` JSON object (keys are member values: strings as themselves, others as JSON text); when array elements are enums it goes on the array property |
| `description` of enum members | `@enumDescriptions` JSON object, keys as in `@enumTitles` |
| `allOf` whose items each contain only `$ref` | Intersection type `X & Y & rest`, e.g. a discriminated union branch `X & { kind: "x" }`; with no rest and only one reference, `X & unknown` |
| `title` of discriminated union branches | `@branchTitles` JSON array in branch order, `null` for branches without `title`; output only when the union node can carry a comment |
| Both `properties` and `additionalProperties` | Index signature written as `(extra type) \| property types...`, with `undefined` added for optional properties; only the extra type in parentheses is read back |
| `x-valueFormat` (storage format of date components) | `@valueFormat format`, value is text |
| The type pointed to by the root `$ref` differs from the default export | `@root` on the root type's comment (modifier tag, no value) |
| Root `$id` (only on the root type) | `@id URI`, value is text |
| Root `x-ui.rules` (only on the root type) | `@rules rule array`, value is JSON |
| Root `x-ui.widgets` (widget modules, only on the root type) | `@widgets module map`, value is a JSON object |
| `x-ui` | `@widget name` when it has only `widget`, otherwise `` @ui `{...}` `` |
| `x-ui` of array elements | Written on the array property: `@itemWidget name` when it has only `widget`, otherwise `` @itemUi `{...}` ``; the n-th tag applies to the n-th level of elements (`items`, `items.items`...), and skipped levels are written as `` @itemUi `{}` `` |
| `errorMessage` | `@errorMessage JSON` (string or object) |

Tags are ordered by the keyword order of normalization rule 7 in `docs/spec/jotl.md` (Chinese). Except for `x-ui` of array elements, element-level constraints and annotations (such as `maxLength` on array elements) have no place to attach a comment, and in non-typia mode are dropped with `JOTL2002`.
The Jotl extension keywords `x-decimals` `x-decimalRange`, as well as `contentSchema` `propertyNames` and `allOf` with non-reference members, have no corresponding notation and are likewise dropped with `JOTL2002`. Fixed shapes the compiler generates for built-in components are not reported: `additionalProperties: false` `x-decimalRange` `x-decimals` on `money` `bigint` value objects (`properties.type` is the `money` or `bigint` constant), and `title` of discriminated union branches in places that cannot carry comments (such as array elements, union branches).
The root `$id` and root `x-ui.rules` (an `x-ui` on the root containing only `version` and `rules` is document-level) are written as `@id` `@rules` on the root type's comment (root `x-ui.widgets` likewise as `@widgets`); without a root they are dropped with `JOTL2002`. Writing `@root` `@id` `@rules` outside the root type (the declaration with `@root`, or the default export when there is none) reports `JOTL2115`; with a root, `tsToSchema` writes `x-ui: { version: 1 }` and the `rules` read onto the root, consistent with the compiler.

Value encoding:

- Text values (body, `@title` etc.): TSDoc syntax characters (backslash, `@`, `{`, `}`, `<`, `>` and backtick) are escaped with a preceding backslash, and `*/` is written as `*\/`.
- JSON values: objects, and values containing TSDoc syntax characters or backslashes, are wrapped in backticks; others are written as plain JSON (e.g. `"欢迎"` `1`).
- Regexes: written in backticks; when containing backticks, newlines or `*/`, starting with a quote, having leading or trailing whitespace, or being empty, they are rewritten as a JSON string in backticks.
- Examples: objects and arrays containing objects are written as `json` code blocks.

Additionally accepted when reading: aliases `@default` `@readOnly` `@examples` `@comment` `@description` (tag names are case-insensitive); backticks around JSON values may be omitted; values that are not valid JSON are treated as strings with a `JOTL2113` warning; TSDoc standard tags (such as `@remarks` `@see`) are silently ignored, unknown tags report a `JOTL2114` warning; tags used on inapplicable types report a `JOTL2115` warning; `@asType` only accepts `integer`, other values report a `JOTL2118` warning.

### typia type tags

With `typiaTags: true`, constraints typia can express are rewritten as type intersections, and `import { tags } from "typia";` is added at the start of the output (imported under an alias when the type name `tags` is taken, and not imported when unused):

- `type: "integer"` → `tags.Type<"int32">` (when both bounds are within int32) or `tags.Type<"int64">`, no longer writing `@asType`.
- Numeric and length constraints → same-named tags such as `tags.Minimum<1>`; `pattern` → `tags.Pattern`; `uniqueItems` → `tags.UniqueItems`; `contentMediaType` → `tags.ContentMediaType`.
- `format` is rewritten only for formats typia supports (list in `TYPIA_FORMATS` of `packages/convert/src/ts/typia.ts`); others (such as `color`) are still written as `@format`.
- `default` that is a string, number, boolean or an array of them → `tags.Default`, otherwise still `@defaultValue`.
- `x-ui` that is an object → `tags.JsonSchemaPlugin<{ "x-ui": ... }>`.
- Nullable types tag only the non-`null` part; interface declarations themselves cannot carry tags, so their constraints are still written as JSDoc. Element-level constraints can be expressed in this mode.

Precondition: the output type-checks with zero type errors against the type definitions of `typia@15.1.0`; other typia versions may have different `tags.Format` values. `tsToSchema` reads tags imported via `import { tags } from "typia"` (including aliases) and restores them to the keywords above (`tags.Type<"int32" | "int64" | "uint32" | "uint64">` changes `number` to `integer`); nullable `(T & tags.X) | null` reads back as `type: [T, "null"]`, so typia-mode output round-trips; the import declaration still reports a `JOTL2108` warning, and other typia tags as well as `tags.X` without the import report `JOTL2106`.

### TSDoc and ESLint configuration

Without loading the presets, TSDoc and eslint-plugin-jsdoc report the protocol's custom tags as unknown tags.

For TSDoc (e.g. eslint-plugin-tsdoc, API Extractor), extend the preset in the project's `tsdoc.json`:

```json
{
  "$schema": "https://developer.microsoft.com/json-schemas/tsdoc/v0/tsdoc.schema.json",
  "extends": ["@jotl/convert/tsdoc.json"]
}
```

For eslint-plugin-jsdoc use `definedTags` (custom tags plus `defaultValue` `privateRemarks`):

```js
import { definedTags } from "@jotl/convert/eslint";

export default [{ rules: { "jsdoc/check-tag-names": ["error", { definedTags }] } }];
```

`extends` in `tsdoc.json` is covered by tests; the behavior of the two ESLint plugins after loading the presets has not been tested in practice, see "确定不修" (Won't fix) in the root `TODO.md`.

### Using in the browser

The main entry `@jotl/convert` (including `schemaToTs` and all migration APIs) does not reference `typescript`, so browser bundles and extensions that use only the main entry do not bundle the compiler.
`tsToSchema` depends on `typescript` and is exported only from `@jotl/convert/from-ts`; importing from this subpath bundles the entire compiler, and the build guard in `apps/playground/vite.config.ts` fails the build when `typescript` ends up in the output.
Running `tsToSchema` in the browser has not been verified, see "确定不修" (Won't fix) in the root `TODO.md`.

## Upgrade: legacy JSON Schema → 2020-12

Detects the input's version and rewrites it step by step to 2020-12 (subschemas under unknown keywords pointed to by `$ref` are upgraded too), adjusts `$ref`s affected by renames accordingly, writes the 2020-12 `$schema` on the root, and orders keywords in normalized order. Each rewrite reports one info diagnostic, usable directly as a change list.

### Minimal upgrade example

```ts
import { upgradeSchema } from "@jotl/convert";

const result = upgradeSchema({
  $schema: "http://json-schema.org/draft-04/schema#",
  id: "https://x.test/a.json",
  type: "object",
  properties: { n: { $ref: "#/definitions/n" } },
  definitions: { n: { type: "number", minimum: 0, exclusiveMinimum: true } },
});
// result.value.schema:
// { $schema: "https://json-schema.org/draft/2020-12/schema", $id: "https://x.test/a.json", type: "object",
//   properties: { n: { $ref: "#/$defs/n" } }, $defs: { n: { type: "number", exclusiveMinimum: 0 } } }
// result.value.version: "draft-04", result.value.versionSource: "declared"
// result.diagnostics: JOTL3101 JOTL3105 JOTL3102 JOTL3120 JOTL3119, all info
```

For cross-file references use `upgradeDocuments`, with the caller providing a callback that fetches documents by URI:

```ts
import { upgradeDocuments } from "@jotl/convert";

const result = await upgradeDocuments("https://x.test/main.json", {
  load: async (uri) => ({ value: await fetchJson(uri), diagnostics: [] }),
});
// result.value.documents: keyed by document URI, in load order, the first being the entry; each document's version is detected from its own $schema
```

### Version detection

`detectVersion(schema, options?)` takes the first item that holds in the following order; `upgradeSchema` and `upgradeDocuments` use the same internally:

1. `$schema` is recognizable (http and https, with or without an empty fragment, and the corresponding hyper-schema): `versionSource` is `"declared"`; when it differs from the `version` option, `$schema` wins and `JOTL3006` is reported. JSON Schema stable v1's `https://json-schema.org/v1` (and `/v1/<year>`) is read as `2020-12`, and `$schema` is rewritten to 2020-12 on output (`JOTL3119`).
2. The caller gave `version`: `"specified"`; in this case, if `$schema` is present but unrecognizable, `JOTL3004` is reported.
3. Inferred from characteristic keywords: `"inferred"`, reporting `JOTL3007` (info). With Swagger features (such as `x-nullable`) it is `swagger-2.0`, with OpenAPI 3.0 features (such as `nullable`) `openapi-3.0`; otherwise, with legacy features, the corresponding lowest version among them; with only newer features, the lowest version that supports all of them.

- With neither `$schema` nor distinguishing keywords, a `JOTL3001` error is reported and `version` must be specified; e.g. `upgradeSchema({ type: "string" })` fails, `upgradeSchema({ type: "string" }, { version: "draft-07" })` succeeds.
- draft-03 is not supported, reporting `JOTL3002`.
- Available version values are in `SCHEMA_VERSIONS` of `src/migrate/upgrade/versions.ts`; use `isSchemaVersion` to check whether a string is valid.

### Public API of upgrade

| Export | Purpose |
|---|---|
| `upgradeSchema(schema, options?)` | Upgrades a single document without modifying the input; returns `Result<UpgradedSchema>`: `{ schema, version, versionSource }`. With errors `value` is `undefined` |
| `upgradeDocuments(entry, options)` | Starting from the entry URI, upgrades it and all documents reachable via its `$ref`s, rewriting cross-document references per the target documents' pointer mappings; returns `Promise<Result<UpgradedDocuments>>`: `{ entry, documents }` |
| `detectVersion(schema, options?)` | Only detects the version, returning `Result<VersionDetection>`: `{ version, source }` |
| `DEFAULT_UPGRADE_OPTIONS` | Default option values |
| `RECURSIVE_ANCHOR_NAME` | The `$dynamicAnchor` name that `$recursiveAnchor: true` is rewritten to |
| `UPGRADE_DIAGNOSTICS`, `upgradeDiagnostic` | Code table and utility to build diagnostics by code |

`UpgradeOptions`:

| Option | Default | Meaning |
|---|---|---|
| `version` | none | Version used when there is no recognizable `$schema`; usually needed for OpenAPI 3.0 / Swagger 2.0 Schema Objects |
| `acceptNewerKeywords` | `true` | Newer keywords that do not exist in the declared version: `true` keeps them with 2020-12 semantics and reports `JOTL3201`; `false` removes them and reports `JOTL3202`; `$defs` is an exception: it is only a container referenced by `$ref` and is kept under both values |
| `onConflict` | `"error"` | On old/new semantic conflicts (`JOTL33xx`): `"error"` reports an error and fails; `"preferDeclared"` follows the declared version; `"preferLatest"` follows 2020-12; the latter two report a warning and state the handling in `related` |
| `uri` | none | Document URI: the base for resolving relative `$id` / `$ref`, also written into the `document` of diagnostic locations |

Example: in draft-07, `minLength` written next to `$ref` is ignored by draft-07 but takes effect in 2020-12, so by default a `JOTL3303` error is reported; with `preferDeclared` `minLength` is deleted, with `preferLatest` it is kept.

`UpgradeDocumentsOptions` is `UpgradeOptions` without `uri`, plus `load: DocumentLoader`.
`DocumentLoader` receives an absolute URI without fragment and returns (or resolves to) `Result<unknown>`:

- When `value` is a document, it takes part in the upgrade.
- When `value` is `undefined` with no error diagnostics, the document does not take part in the upgrade (e.g. a meta-schema built into the validator), and references to it are kept as is.
- When `value` is `undefined` with errors, `JOTL3401` is reported; when the callback throws, `JOTL3402` is reported.

### Diagnostic codes of upgrade

The code range is `JOTL3xxx`, code table `UPGRADE_DIAGNOSTICS` in `src/migrate/upgrade/diagnostics.ts`; locations are JSON Pointers (`location.kind === "pointer"`), with `document` across documents.

| Range | Meaning |
|---|---|
| `30xx` | Input and version detection |
| `31xx` | Step-by-step rewrites, one info each |
| `32xx` | Lenient mode: acceptance or removal of newer keywords, legacy notation in newer documents |
| `33xx` | Old/new semantic conflicts, severity varies with `onConflict` |
| `34xx` | Multi-document loading |

### Known limitations of upgrade

Normalization rule 2 (named types only in the root `$defs`) does not hold for upgrade results; for this and other limitations see "确定不修" (Won't fix) in the root `TODO.md`.

## Fengdie migration: Fengdie schema → Jotl

Lexical and grammar rules follow umo-edit-sdk 0.0.8 as actually used by the Fengdie editor (`parse/schema.l` `schema.yy`). Pipeline: source → umo JSON isomorphic to toJson → JSON Schema 2020-12 → Jotl output by `@jotl/core`'s `print`.
Four rules that affect migration results (referred to below as D1-D4):

- D1 `Date` migrates to a millisecond timestamp integer (`datetime[value_format: 'x']`), so existing Fengdie data passes validation without conversion.
- D2 `group` of first-level fields migrates to the root object's `x-ui.groups`, rendered as groups by group value.
- D3 Information with no corresponding Jotl notation is written to the node's `x-fengdie` (machine-readable, preserved on round trip), not to `$comment`.
- D4 Only fields with `required: true` are required; the rest are optional per Fengdie semantics.

```ts
import { migrateFengdie } from "@jotl/convert";

const { jotl, schema, umo, diagnostics } = migrateFengdie(
  `Object(首页) {
    title(标题): String[maxLength: 20, required: true]
    start(开始): Date
  }`,
  "home.fengdie",
);
// jotl:
// Root(首页): {
//   title(标题): string[maxLength: 20]
//   start(开始)?: datetime[value_format: 'x']
// }
```

| Export | Purpose |
|---|---|
| `migrateFengdie(input, file?)` | input is source, umo JSON text (first non-whitespace character `{`) or a umo JSON object; returns `{ jotl?, schema?, umo?, diagnostics }`, with `jotl` `undefined` on errors. `schema` is deeply equal to the result of compiling `jotl` again |
| `fengdieToUmoJson(source, file?)` | Source → umo JSON, also returning `origins` (node to source location) |
| `umoJsonToSchema(umo, { origins?, file? })` | umo JSON → unsorted 2020-12 document; without `origins` diagnostic locations are pointers into the umo JSON |
| `detectMigrateInput(text)` / `umoJsonFeature(json)` | Determine whether the input is Fengdie source, umo JSON or a regular JSON Schema, and give the basis |
| `MIGRATE_DIAGNOSTICS` | Fengdie diagnostic code table |

- Lexical or syntax errors (`JOTL8001`-`JOTL8005`) stop at the first error, as jison does; umo JSON parse failures and invalid structure are `JOTL8006` `JOTL8007`.
- All other problems are warnings (`JOTL81xx`) and do not affect the result; warnings are reported only for information that is actually lost or rewritten, not for information preserved losslessly in `x-fengdie`. Constructs that make umo-edit-sdk's toJson throw (writing metadata for types without a metadata table, such as `Array<string>[...]` `Component[...]` root `OpenAction[...]`) drop that metadata during migration and report `JOTL8118`.
- Strings and arrays are allowed to be empty by Jotl default; an explicit `minLength: 0` means unlimited and is not written out.
- `x-fengdie` is written as `x_fengdie` in Jotl (D3); structural information occupies `type` `lottery` `public` `regExpFlags`, and same-named metadata is recorded as `metaType` etc. instead.

### Type mapping

| Fengdie type (umo `type`) | 2020-12 / Jotl | Notes |
|---|---|---|
| `String` (and omitted type) `Text` `RichText` `URL` `Color` `File` `Image` `Number` `Boolean` | `string` `text` `richtext` `url` `color` `file` `image` `number` `boolean` | Unknown type names fall back to `string`, reporting `JOTL8111` |
| `Date` | `datetime[value_format: 'x']` | The Fengdie editor uses a date-time picker and the data is a millisecond timestamp; the schema is `{type: integer, minimum: -MAX_SAFE_INTEGER, maximum: MAX_SAFE_INTEGER, x-valueFormat: 'x', x-ui: {widget: 'datetime'}}` |
| `Enum` | `enum`; `oneOf` when there are descriptions | `multiple: true` means multi-select; single-select with 2-5 items writes `widget: 'radio'`, multi-select writes `widget: 'checkbox'`; with no members it becomes a string (`JOTL8114`) |
| `Array<string>` `Array<number>` | `array[array_item: 'string' / 'number']` | |
| `Object` `Action` `OpenAction` `Spm` | Object | `Spm` is fixed to the three strings `spma` `spmb` `spmc` |
| `Array` | Array of objects | |
| `Module` `ModuleArray` `namespace.Component` `namespace.Component[Array]` | Object / array of objects | `namespace` `component` `version` `url` `dist` are recorded in `x-fengdie` |
| `Box` `Resource` `Plugin` `Animation` `Video` | Objects shaped like umo-edit-sdk mock data, not closed | |
| `Component` | `string` | Component instance id |
| Root `Lottery` / `public` | Object | `x-fengdie.lottery` / `x-fengdie.public`, no warning |
| `export a ... export b ...` | Each becomes a `$defs` type, the first being the root | Names that are not PascalCase are renamed per `print`'s rules, reporting `JOTL8117` |

The original type names of `Component` `Box` `Resource` `Plugin` `Animation` `Video` `Action` `OpenAction` `Spm` `Module` `ModuleArray` and namespace types are recorded in `x-fengdie.type`.

### Metadata mapping

| Fengdie metadata | Destination |
|---|---|
| Description `(...)` / `description` | `title` / `description` |
| `default` `defaultValue` | `default`, corrected by type (`JOTL8107`), dropped when violating constraints (`JOTL8108`); when both appear `default` wins (`JOTL8115`) |
| `minLength` `maxLength` | Strings: `minLength` `maxLength`; arrays: `minItems` `maxItems` |
| `min` `max` / `step` | `minimum` `maximum` / `x-ui.props.step` |
| `regExp` | `pattern`; `"/^https:/gi"` has its delimiters removed; `i` is rewritten into the pattern (letters become `[hH]`, character classes get the other case added), and when Unicode property classes, backreferences etc. make a safe rewrite impossible it is kept as is with `JOTL8119`; `g` is ignored; `m` `s` `u` `y` report `JOTL8120`; flags that did not take effect are recorded in `x-fengdie.regExpFlags` |
| `errorMsg` | `errorMessage` |
| `placeholder`, and `width` `height` `maxWidth` `maxHeight` `aspectRatio` `maxSize` `setDefaultColorTo` of `Image` | `x-ui.props` |
| `if: "$.path"` | `x-ui.visibleIf` (Jotl `root_if`); other forms are recorded in `x-fengdie` |
| `required: true` | Parent object's `required` (D4) |
| `group` of first-level fields | Root object's `x-ui.groups`: `normal` 常规 / General, `advance` 高级 / Advanced, `developer` 开发者 / Developer, `operator` 运营 / Operations (title language follows the global language; D2); deeper levels are recorded in `x-fengdie` |
| `showKey` | `x-ui.summary`; dropped when not an element field (`JOTL8106`) |
| Others in the allowlist (`rule` `source` `searchType` `sourceType` `reuseable` `autoFetch` `entityType` `mappingRuleId` `defaultSourceType` `ucdp` `spmC` `spmD` `configId` `crossApp` `i18n` etc.) and `custom*` | Same-named entries in `x-fengdie`, no warning (D3) |
| Outside the allowlist | Dropped, reporting `JOTL8105` (consistent with toJson) |

Per-type metadata allowlists are in `UMO_META_KEYS` of `src/migrate/fengdie/umo-types.ts` (taken from umo-edit-sdk `lib/types.js`).
