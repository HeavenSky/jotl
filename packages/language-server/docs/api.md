# Call the language service from code

**English** · [简体中文](../zh/docs/api.md)

After reading this page you can run every language feature as a plain function, for example in a web editor, a linter or a test, without an LSP connection. You need the package installed as in the [quick start](../README.md).

## Run a feature on a string

Each function takes the document text, its URI and, where it applies, an LSP position or range:

```js
import { getCodeActions, getDiagnostics, getHover, getPreview } from "@jotl/language-server";

const uri = "file:///home.jotl";

const source = "title: string\n";
const [diagnostic] = getDiagnostics(source, uri); // JOTL1036: only types can be declared at the top level
getCodeActions(source, uri, diagnostic.range);
// [{ title: "Wrap in `Root: {...}` and mark `<root/>`", kind: "quickfix", isPreferred: true, edit: ... }]

getHover("Home: {\n  title: string[maxLength: 20]\n}\n", uri, { line: 1, character: 3 });
// contents: Markdown "Field `title`" followed by the JSON fragment { "type": "string", "maxLength": 20 }

getPreview("Home: { title: string }", uri);
// { schema: JSON text, typescript: "// Generated by Jotl. Do not edit.\n\nexport interface Home {...", diagnostics: [], ... }
```

- Positions and ranges follow LSP: lines and columns start at 0, columns count UTF-16 code units. Compiler positions start at 1 and are converted for you.
- `getPreview` is the exception: its `PreviewDiagnostic`s keep lines and columns starting at 1, as described in [Show a preview](editor-integration.md#show-a-preview).
- Text comes in the global language of `@jotl/core`, English unless you call `setLocale("zh-CN")` first.

## Functions

| Function                                                 | Returns            | Behavior                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `getDiagnostics(text, uri, options?)`                    | `Diagnostic[]`     | Compiler diagnostics plus the unregistered-widget check (`JOTL7001`), sorted by position; `source` is `"jotl"`                                                                                                                                                                                   |
| `getCodeActions(text, uri, range, options?)`             | `CodeAction[]`     | Every fix attached to diagnostics that touch `range`; a fix is marked preferred when it is the only one for its diagnostic                                                                                                                                                                       |
| `getCompletions(text, position, options?)`               | `CompletionItem[]` | Completion for the context at the cursor; see below                                                                                                                                                                                                                                              |
| `getHover(text, uri, position, options?)`                | `Hover \| null`    | Type names, type references and field keys show the compiled JSON fragment, cut after `MAX_FRAGMENT_LINES` (60) lines; built-in components, extension components (with their underlying schema; a declaration in the root `widgets` metadata wins), metadata keys and markers show a description |
| `getDefinition(text, uri, position)`                     | `Location[]`       | The declaration of the top-level type under the cursor, from a reference (in component position or a type string) or the declared name                                                                                                                                                           |
| `getReferences(text, uri, position, includeDeclaration)` | `Location[]`       | References to that top-level type in this file                                                                                                                                                                                                                                                   |
| `getDocumentSymbols(text, uri)`                          | `DocumentSymbol[]` | Outline: one item per top-level type, with fields, branches and enum members nested                                                                                                                                                                                                              |
| `getPreview(text, uri, options?, config?)`               | `PreviewContent`   | Compiled schema and TS with their diagnostics; `config` (`{ file, modules }`) is passed through as `configFile` and `modules`. TS uses the compiled `defaultExport` as its default export                                                                                                        |

`getCompletions` offers, depending on where the cursor is:

- In component position: built-in components, types declared in the file, and extension components (including names declared by the root `widgets` metadata).
- Inside metadata `[...]`: the keys that apply to the component (`META_KEY_TARGETS`).
- As values: `widget` (built-in widgets that `acceptsWidget` allows for the component's data shape, the default first, then registered names), `decorator`, `value_format` (common formats for each date component, timestamps and four aliases) and condition `op`.
- Names inside type strings, and the markers `<root/>` and `<default/>`.

## Options

`options` is a `LanguageServiceOptions`:

| Field               | Meaning                                                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `registeredWidgets` | Registered widget names; default empty, so only `BUILTIN_WIDGETS` of `@jotl/form/core` are known. UpperCamelCase names are also extension components |
| `widgets`           | Underlying schemas of registered names; extension components missing here compile as `string`                                                        |

The functions never read `jotl.config.json`. To apply one, read it with `readJotlConfig` from `@jotl/core` and merge `config.widgets` with `withConfigWidgets(options, widgets)`; on a name clash the configuration wins and names already in `options` are kept.

Helpers for building options from client messages:

- `readInitializationOptions(raw)` reads `registeredWidgets` from `initializationOptions` or the `jotl` settings section.
- `readLocaleOption(raw)` reads `locale` from the same objects and returns `undefined` when it is missing or not a non-empty string.

## Schemas for JSON editing

- `createXUiJsonSchema()`: the schema for `x-ui` in JSON Schema files, with `$id` `X_UI_JSON_SCHEMA_ID`. The VS Code extension writes it to `x-ui.schema.json` when packaged.
- `createJotlConfigJsonSchema()` and `JOTL_CONFIG_FILE`: re-exported from `@jotl/core`; the schema of `jotl.config.json` and its file name. The VS Code extension writes the schema to `jotl.config.schema.json`.

Diagnostic codes are listed in [Connect an editor](editor-integration.md#diagnostic-codes); the code table is exported as `LSP_DIAGNOSTICS`.
